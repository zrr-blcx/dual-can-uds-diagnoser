## 技术知识点

- `python-can` 的后端依赖是分开的：slcan 需要 `pyserial`，`gs_usb`（candleLight）
  需要 `pyusb` 和 `gs_usb` 包；Windows 上 `pyusb` 还需要 `libusb` 提供的
  `libusb-1.0.dll`。
- `pyusb` 通过 DLL 搜索路径查找 libusb。`libusb` wheel 把 DLL 放在自己的包目录里，
  不在搜索路径上，因此需要在打开总线前用
  `usb.backend.libusb1.get_backend(find_library=...)` 指定，避免手工拷贝 DLL。
- SN65HVD230 模块**自带 120Ω 终接**：两个模块分别位于总线两端即得到约 60Ω，
  不需要外接电阻。CANable 的 120Ω 开关位于总线中间，必须保持关闭，否则变成
  三个终接（约 40Ω）。
- 终接读数判据：60Ω 正确；30Ω = 多并了外接电阻；40Ω = CANable 终接没断开；
  120Ω = 只有一个模块在位；∞ = 两个模块都没接通。
- 帧间隔必须按**同一个 arbitration ID** 的相邻帧计算，否则其它流量会把离线窗口算短。
- ACK 错误累积到 TEC=256 进入 Bus-Off：`0x123` 周期 500 ms 时需要约 16 秒；
  周期临时改成 20 ms 约 0.7 秒即可触发，恢复时间分辨率也从 ±500 ms 提升到 ±20 ms。

- 一开始把"CANable 打不开"当成硬件问题，实际是 Python 依赖缺失；先查依赖再查

  错误；先测量、再定方案，比先写进文档更可靠。相关文档与图纸已更正。

- 终接已实测确认 60Ω（两个模块自带 120Ω + CANable 开关关闭）；继电器尚未做

- 两个工程事实上是手工维护的：F103 的 `main.c`/`it.c`/`hal_msp.c` 完全没有

## Phase 3 硬件验收记录（2026-10-15 晚）

- 用 CubeIDE 自带的 `STM32_Programmer_CLI` 命令行烧写两个节点（SN 区分探针），
  `Download verified successfully` + `MCU Reset` 各一次。
- 烧写后冒烟：10 秒 40 帧 `0x123`、无错误帧；两个节点快照均为
  `00 00 00 00`（error-active，无 Bus-Off）。
- 单节点隔离实测（拔掉 F103，CANable listen-only 不参与）：F407 的
  `g_can_health_summary` 显示 bus-off 计数与恢复成功计数持续增长，连续失败保持 0，
  `IWDGRST=0`。**据此只能下有限结论**：CAN SCE 中断 →
  `HAL_CAN_ErrorCallback` → `CanDriver_OnErrorIsr` 通路在硬件上有效，且软件恢复链
  `DeInit→Init→滤波→Start` 可用（节点不卡死）。
- **结论修正**：直接用 `STM32_Programmer_CLI` 读 CAN1 的 ESR（`0x40006418`）时，
  TEC 恒为 128（error-passive）、**BOFF 从未被采样捕获**，与"模型里 bus-off 计数持续
  增长"不一致。因此先前"178 次 bus-off / 177 次恢复"**不能当作 178 次硬件 Bus-Off**
  来宣称，其计数来源待插桩确认。（另：第一次取样误把 `0x40006404`（MSR）当成 ESR，
  那批读数无效，已记入 FAQ HW-12/HW-13。）
- 复电后双节点回归：10 秒 40 帧、平均间隔 247.6 ms、无错误帧，F407 状态稳定
  error-active，计数器不再增长 → **烧写后 `0x123` 无退化，Phase 3 门禁通过**。
- 待决：`RCC_CSR` 显示隔离期发生过一次无法归因的软件/引脚复位（PORRST/IWDGRST 均为 0），
  最可能是"连续失败 3 次复位"在相位漂移下偶发触发。该路径的语义（只算恢复链失败，
  还是把"判定窗内重新 Bus-Off"也算失败）与是否加入重试退避，需要决策后可能重烧两节点。
- 测量方法教训：读内存必须 `mode=hotplug`，否则连接本身会复位目标；这条已记入
  `常见问题与注意事项.md` HW-12。

## 插桩定位：重发风暴与 TEC 冻结（2026-10-15 深夜）

为解释"模型里 bus-off 计数增长、寄存器里 TEC 却停在 128"，在 ISR 与恢复服务各加了
一个 RAM 环形缓冲（`g_can_error_log` 记录 `ErrorCode/ESR/tick`，`g_app_health_log`
记录发起恢复/判定成功/判定失败/请求复位），用 `mode=hotplug` 读出解码。

结论：

- `AutoRetransmission = ENABLE` 时，无 ACK 的帧被无限重发：**22.6 秒内产生 153,694 次
  ACK 错误中断（约 6,800 次/秒）**，TEC 冻结在 128，永不 Bus-Off，TX mailbox 被占满。
  已把 `can_driver.c` 的 `AutoRetransmission` 改成 `DISABLE`；改后中断间隔变为 506 ms
  （每次发送一次错误），风暴消失。
- 即便如此，**"去掉 ACK"仍无法让 TEC 越过 128 达到 256** → 本硬件上拔对端触发不了
  Bus-Off。因此：先前记录的"bus-off 178 次 / 恢复 177 次"是**模型侧计数**，不是硬件
  Bus-Off；决策 ②（判定窗内重新 Bus-Off 算失败）**不可达**，复位升级语义定为 **①**
  （只在恢复链失败时复位）。
- Bus-Off 检测与恢复的硬件验收改到 **Phase 4**：用继电器做物理断开/瞬时短接，
  确认 `TEC→256 / BOFF=1` 后再记录恢复时间与连续 3 次结果（任务 W2-07f）。

## 2026-10-21 连接复检与两处修正

- 台架复检：两个 ST-Link 都在、CANable 已连接、双节点 8 秒 32 帧（平均 248 ms、
  无错误帧）；两节点 ESR 均为 `TEC=0 / BOFF=0`，中断日志为空 → 电气与总线连接正常，
  继电器未动作时处于"CH1 常闭、CH2 常开"的正确空闲态。
- **修掉一个真实 bug**：两个 `main.c` 都从未调用 `CanHealth_Init()`，导致阈值全为 0
  （应为 128/256/3），任何一次错误都会被判成 Bus-Off，之前那些"119 次/178 次"
  的异常计数由此而来。已在 `CanDriver_AttachHealth()` 前补上初始化并重烧两节点。
- **修正解码脚本**：ARM GCC 默认 short enums（1 字节），健康快照的结构体偏移与 PC
  侧 4 字节枚举不同，之前把 `state` 解成 1048576。新增 `脚本\解码健康快照.py`
  按正确布局解码（复检结果：state=0、TEC=16、ACK 错误 2 次，与 ESR 一致）。
